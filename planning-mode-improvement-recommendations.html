Make planning mode implementation-ready, traceable, and easy to execute

Improve the existing /plan workflow by preserving decisions, making requirements observable, enforcing traceability, and rendering an offline-first plan that people can scan, trust, and implement without rediscovering intent.

Recommendation

Keep the current single-session, planning-only model. Do not copy Matt Pocock’s issue-tracker workflow or add persistent planning maps. Instead, adopt its useful ideas inside one plan: a dependency-aware question frontier, explicit decisions, an honest fog/deferred-unknowns ledger, and tasks that represent independently verifiable slices.

North-star outcome

A published plan should let a fresh implementation agent answer: what must change, why, what is already decided, what is still uncertain, where the verified seams are, how each requirement is proven, and whether the artifact being executed is exactly the artifact that was approved.

Preserve intent

Decisions are first-class

Record user choices, evidence-based choices, alternatives, rationale, consequences, and reversibility. Do not lose them between interview and /execute-plan.

Prove completion

Requirements have observable oracles

Link requirements to acceptance criteria, tasks, validations, and expected evidence—not adjectives such as “robust” or “production-ready.”

Avoid false precision

Every concrete claim has provenance

Mark it observed in the repository, chosen by the user, source-backed, assumed, proposed, or unknown. Exact existing paths are useful; invented paths are not.

Make it legible

HTML is semantic first, visual second

Use a table of contents, task index, strong hierarchy, print styles, generated relationship tables, and diagrams derived from the same structured plan data.

Target planning flow

“Deep detail” should be earned by evidence. The plan should become more specific as the agent inspects the repository and resolves material decisions—not by inventing implementation details upfront.

Wayfinding adaptation

  • Maintain an internal ledger of known, decided, unknown, deferred due to dependency, and out of scope.
  • Ask a question only when the answer can change architecture, public behavior, data handling, validation, compliance, or scope.
  • Ask for user decisions; inspect repository facts yourself.
  • Recompute the frontier after each answer instead of continuing stale, speculative questions.

Grilling adaptation

  • Use native Pi select/input UI, one material question at a time.
  • Offer 2–5 mutually exclusive options, a recommendation, why the answer matters, and free text.
  • Provide an enforced “skip remaining questions; apply best judgment” option.
  • When skipped, record consequential planner judgments as provisional decisions or assumptions—not as invisible reasoning.

What needs to change in the current implementation

The current package has a sound baseline: planning-only prompt boundaries, detailed What/Why/How fields, cycle checks, safe HTML escaping, atomic writes, embedded Markdown, and explicit execution approval. The following gaps prevent a stronger claim that every result is implementation-ready.

Use a traceable plan data model

Do not merely add longer strings. Add small, linked structures that make plan intent inspectable and support a deterministic coverage audit. 

REQ-01 ──satisfied by──▶ TASK-03 ──verified by──▶ VAL-05
    │                         │
    ├──accepted by──▶ AC-02   └──implements──▶ DEC-04
    │
    └──supported by──▶ EVID-07 (observed repository contract)
Entity Minimum fields Required links / rules
Evidence ID, claim, source type (repo, user, external), source pointer, confidence, notes Existing file/module claims reference observed evidence. Proposed paths are labeled proposed.
Requirement REQ-*, observable statement, rationale, priority, evidence IDs Has at least one acceptance criterion.
Acceptance criterion AC-*, requirement IDs, precondition/action/outcome, edge or failure case Has at least one validation method and expected evidence.
Decision DEC-*, context, choice, alternatives where consequential, rationale/evidence, consequences, reversibility, status Links affected requirements, modules, or tasks. A skipped interview decision is marked provisional.
Task TASK-*, What, Why, ordered How, verified/proposed files, dependencies, parallel safety, expected behavior Links a requirement/criterion or is explicitly foundational with downstream dependents.
Validation VAL-*, level, command/procedure, preconditions, expected output/evidence Covers one or more acceptance criteria. State manual procedure when no command exists.
Unknown / assumption statement, impact, status, owner, resolution point, fallback High-impact unknowns block publication; lower-impact ones need a trigger and fallback.
Important constraint: do not create bureaucratic ceremony.

Require alternatives and reversibility discussion only for consequential architecture, data, security, public-contract, or compliance choices. A routine decision that follows an established repository pattern should cite the pattern and move on.

Make the HTML plan easy to read—and diagrams trustworthy

The recommended MVP is a static, semantic, offline-first HTML file. The renderer should generate all visual representations from the same validated plan view model that produces task cards and canonical Markdown.

Recommended MVP

Inline SVG dependency map + visible HTML table

  • Generate a bounded task DAG from tasks[].dependsOn.
  • Use deterministic topological layers, safe text labels, and stable anchors.
  • Place a visible dependency table directly below it: task ID, title, predecessors, downstream work, execution order.
  • Keep SVG decorative (aria-hidden) when the adjacent table completely expresses it, or expose one concise SVG name/description—not both verbose representations.
  • Fall back to table-only for cycles or oversized graphs.
Avoid at runtime

Browser-loaded Mermaid and arbitrary rich SVG

  • A CDN module makes a local file network-dependent and increases executable attack surface.
  • Free-form Mermaid is a second, drifting source of truth unless it is derived from structured data.
  • Do not inject user-authored markup, foreignObject, event handlers, styles, URLs, or raw third-party SVG into the artifact.
  • Graphviz or Mermaid can become optional publish-time layout adapters later, emitting only audited static SVG plus a text equivalent.

Renderer architecture

validated PlanDraft
        │
        ▼
normalizePlanView(plan)
        ├──▶ HTML sections, table of contents, task cards
        ├──▶ canonical Markdown for execution
        ├──▶ buildTaskGraph → layoutTaskGraph → inline SVG
        ├──▶ dependency relationship table
        └──▶ traceability matrix (later)

Accessibility and print baseline

  • One descriptive h1, nested headings, stable section/task anchors, and a linked table of contents.
  • Required content remains visible; do not hide acceptance criteria, risks, tasks, or the only text alternative in <details>.
  • Use system fonts, readable line length, keyboard-visible focus, AA text contrast, and meaning that does not depend on color.
  • Allow horizontal scrolling only inside a two-dimensional diagram wrapper; prose remains responsive at narrow widths.
  • Add @media print and @page rules; test A4 and Letter PDF output in Chromium, Firefox, and Safari.
  • Use a restrictive file-friendly CSP and context-appropriate escaping. CSP is defense in depth, not a replacement for escaping.

Delivery roadmap

Phase 0 · integrity

Prevent executing the wrong plan

P0 Retain the published candidate digest; verify artifact metadata and embedded Markdown hash before implicit approval/execution. Add tamper and same-slug replacement tests.

Phase 1 · planning truth

Preserve decisions and remove ambiguity

P1 Add decisions/provenance, enforce skip-all, choose unambiguous task hierarchy semantics, and render stored dependencies consistently in HTML and Markdown.

Phase 2 · readiness

Trace requirements to proof

P1 Add requirement, acceptance, validation, and evidence links plus a pre-publication coverage report. Make empty evidence, unexplained N/A, and orphaned criteria fail validation.

Phase 3 · reading experience

Replace runtime visualization

P2 Build the renderer-owned task graph, relationship table, anchors, task index, empty states, paragraph-preserving fields, print CSS, and offline artifact tests.

Phase 4 · advanced planning

Typed architecture and traceability views

P3 Introduce a typed architecture graph and optional, publish-time Mermaid/Graphviz adapters only after the MVP proves useful on real plans.

Do not start with a general-purpose diagram engine.

First deliver a simple dependency map that is completely generated from existing task data. It will solve navigation and ordering now, prove the projection architecture, and avoid making arbitrary diagrams a new security and maintenance surface.

Publish quality gates

Before plan_publish creates an artifact, run this audit and show its results inside the final plan.

Block publication when

  • A correctness-, contract-, data-loss-, compliance-, or acceptance-changing question remains unresolved without explicit user approval to defer it.
  • A requirement has no acceptance criterion, an acceptance criterion has no validation, or a task has no reason for existing.
  • Dependencies are invalid, cyclic, ambiguous, or differ between HTML and canonical Markdown.
  • Repository-specific claims use unverified paths, symbols, commands, line numbers, or target numbers.
  • Findings/evidence are empty, engineering “N/A” lacks rationale, or a task uses placeholder/generic implementation prose.

Require each task to state

  • What: the behavioral or structural result.
  • Why: requirement, decision, risk, or existing contract it serves.
  • How: ordered edits, interfaces/data/error behavior, compatibility impact, and test changes.
  • Where: observed existing modules vs clearly proposed new modules.
  • Proof: validation command/procedure, preconditions, expected signal, and acceptance IDs covered.

Suggested plan-quality fixtures

  1. A small localized bug fix: prove the format does not over-engineer straightforward work.
  2. A brownfield feature with data migration: verify decisions, rollout/rollback, compatibility, and end-to-end validation.
  3. A greenfield feature with real fog: prove the plan represents uncertainty honestly instead of inventing future tasks.
  4. Adversarial fixtures: nonexistent paths/commands, vague but long How text, circular dependencies, orphaned acceptance criteria, tampered HTML, and malicious diagram labels.

Evidence and source notes

The recommendations combine a read-only audit of this repository with the primary sources below. “Wayfinding” and “grilling” are adapted concepts; Pi should keep them internal to its single-session planning workflow, not reproduce Matt Pocock’s multi-session issue-map process.

  • Anthropic — Claude Code best practices: explore, plan, code, and use executable verification.
  • Anthropic — Building Effective AI Agents: use transparent plans, environmental ground truth, and the simplest workable system.
  • GitHub Spec Kit and its specification, clarification, task, and analysis templates: staged specification, requirements/acceptance traceability, clarification, and consistency checks.
  • GitHub Copilot task best practices: clear task context, acceptance criteria, and relevant file directions.
  • Matt Pocock skills—especially wayfinder, grilling, to-spec, and to-tickets.
  • MDN Content Security Policy and OWASP XSS Prevention Cheat Sheet: strict resource controls and contextual output encoding.
  • WCAG 2.2, W3C SVG accessibility guidance, and MDN printing guidance: semantic hierarchy, text alternatives, reflow, contrast, and print behavior.
Terminology correction

No standalone Matt Pocock “diagram drawer” skill was verified in the current public skills repository. The recommended approach is therefore an internal renderer capability: a bounded diagram projection derived from validated plan data, not a dependency on a named external skill.
