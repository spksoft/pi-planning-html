Smarter Pi.
Less wasted compute.

Choose the right model + reasoning effort for a task, preserve user control, and optimize for work that actually succeeds—not merely cheap tokens.

1. Build an advisor first, not a second autonomous router

The most valuable feature: inspect a prompt or a verified plan task and show the cheapest eligible, sufficiently reliable model/effort pair, why it fits, when to escalate, and the evidence behind that recommendation.

Initially keep execution unchanged. Add opt-in application only after real Pi dispatch tests and workload evaluations pass.

Intelligence

Understand the task

Use uncertainty, dependency depth, change risk, verification strength, context needs, and language—not prompt length or keywords alone.

Efficiency

Price the whole job

Include selector calls, tool calls, context replay, cache misses, failures, verification, and repair. An expensive model at low effort can beat a cheap model that retries.

Trust

Know when not to guess

Preserve explicit choices. Mark unfamiliar tasks uncalibrated. Keep a capable baseline when the cheaper option has no reliable evidence.

Architecture choice: Pi Planning HTML owns task evidence, HTML explanations, and integrity-aware handoff. pi-model-roles owns model-role configuration and selection. The execution host owns model application, permissions, and launches. One routing owner per boundary prevents two selectors charging for—and overruling—the same prompt. [R1] [R3]

Not a promise: no predictor can know the best model perfectly before execution. Treat routing as a calibrated decision under uncertainty, with an explicit “keep current / insufficient evidence” outcome.

5. How Pi should predict task fit

Step A — build a compact task profile

Inputs to prediction
SignalEvidenceConservative interpretation
Task familyExplanation, extraction, localized fix, feature, debugging, architecture, review, research.Mixed intent is not automatically “routine.” A single prompt can span several families.
UncertaintyMissing acceptance oracle, unresolved decisions, unfamiliar APIs, ambiguous behavior.Missing evidence means unknown—not easy. Research or clarify before claiming an optimal route.
Risk and blast radiusAuthentication, persistence, destructive operations, public interfaces, dependency fan-out.“Just fix auth” is short but can be high risk. File count alone is not complexity.
VerifiabilityReproduction, unit/contract/e2e oracles, review requirements, rollback plan.Reliable checks make cheaper-first work more defensible. A schema-valid plan is not proof the design is correct.
Working contextEstimated instruction + tool-schema + retained history + task input + output reserve.A 20-word task can need a huge repository context. Never route using user-message tokens alone.
Language and modalitySelected question language, code language, images/documents required by the work.Thai is a competency requirement, not a complexity penalty. The same intent in Thai and English should follow equivalent policy.

Step B — filter, then choose a pair

  1. Honor pins and policy. An explicit model/effort choice wins. A paused or disabled selector stays paused. If that choice cannot satisfy a hard capability constraint, explain the conflict instead of silently overriding it.
  2. Remove ineligible candidates. Check allowlist, exact identity, capabilities, context, and policy constraints. Unknown privacy/capability status is not permission to proceed.
  3. Try deterministic selection. A user-chosen role or a trusted, tightly scoped task template may bypass semantic classification. An arbitrary request merely containing “typo” may not.
  4. Classify only if useful. At most one bounded, tool-free selector request per decision. Ask for a task category or allowed role ID, not a full solution or arbitrary model name. Charge its overhead to the task.
  5. Choose model × effort jointly. Use measured outcomes for each supported pair. If evidence is insufficient, return uncalibrated and retain the configured capable baseline.
  6. Revalidate before applying. Check session identity, queue/idle state, pins, model scope, and capability freshness. Record the actual request pair separately from the proposed pair.
Proposed decision objective:
  choose the eligible (model, effort) pair with lowest expected total cost
  subject to the owner-defined quality floor and latency constraint.

Expected total cost = selector + execution + verification
                    + switching/context replay + expected repair.

Use a lower confidence bound on task success when calibrated data exists.
Without enough data: no probability claim; keep the baseline or ask.

An LLM saying “confidence: 0.95” is not calibration. Learn confidence from held-out outcomes and report uncertainty/sample size. Do not collect private chain-of-thought to explain routing; use observable features and bounded reason codes.

7. Integration without breaking the existing workflow

Two entry paths, one selector owner

  • New prompt: keep model-roles’ supported idle TUI input path. It can route raw /plan … before expansion. Do not add a second global input router in Planning HTML.
  • Approved plan: a proposed optional bridge inside /execute-plan verifies the artifact first, prepares a bounded task/whole-plan summary, then requests a decision before dispatch. Recommendations in a plan do not authorize execution.
  • Independent child task: select before a permitted native launch, only when the launcher exposes resolved model pins and allowlists. The parent keeps integration and final validation. Unsupported external CLI mappings remain unsupported.
  • Active tool loop: leave it alone. No automatic switches from context, no concurrent “better model” replacement, and no rerouting on each tool result.

The existing event service pi-model-roles:select:v1 returns a decision and does not mutate the parent. Its current request accepts task text, pins, allowlists, and image requirements, not this proposal’s rich task-profile object. A bounded text projection can bridge v1; richer cost-aware selection would need a reviewed API/configuration revision. [R5]

Compatibility gate: the event service does not automatically provide the parent’s manual-pause state for independent requests. If the planning bridge cannot establish routing ownership and pause/pin state publicly, it must stay recommendation-only. Do not infer ownership from environment variables or private controller fields.

Application is not atomic: on tested Pi 0.85.1, setModel() has no cancellation or conditional session-state argument. A switch already in progress may finish after cancellation or navigation. Preflight guards reduce risk but do not solve that SDK limitation; keep the user informed, check the active pair after an interruption, and do not claim automatic rollback. [R4]

Whole-plan versus per-task: the current executor starts one normal agent run. MVP recommends a parent pair for the whole plan and may display per-task advice. It does not promise automatic phase switching or task-by-task execution.

  • Do not mistake prose for typed data. The existing artifact exposes canonical Markdown for execution, not a public task-profile parser. For durable task-aware routing, add a small versioned routing manifest at publication, generated from validated task data—not inferred later with regexes from arbitrary HTML.
  • Integrity binds the recommendation. Include advisory data in candidate/Markdown parity and hash a typed manifest when introducing it. Validate its link to the candidate.   • Separate history from current availability. An approved plan stores the recommendation snapshot; execution rechecks availability, rates, and pins. Explain changes in a separate receipt, never silently rewrite the approved HTML.
  • No false success state. An emitted kickoff is “dispatched,” not “implemented.” Completion needs named validation evidence from the existing executor or a user-attested outcome. Missing telemetry remains unknown.

9. Cost controls that actually improve efficiency

Optimize cost per successful task

All spend ÷ validated successes

Also report success rate and total attempted tasks, so the metric cannot improve by abandoning hard work. Include failed attempts, selector overhead, tests/review, external tools, and supported child usage.

Do not equate billing with usage

Subscription/OAuth quota, API list prices, local inference, and provider credits are different. Track tokens and latency for all routes; show monetary estimates only where the pricing basis is known.

A small worked example—illustrative, not measured

Suppose a strong-model attempt costs $0.80 including its verification. A routine attempt costs $0.15, routing costs $0.01, and its extra verification/context overhead is $0.04. If 20% require one strong repair:

Expected cheap-first cost = $0.01 + $0.15 + $0.04 + 0.20 × $0.80
                          = $0.36 per task.

If 80% need repair instead: $0.20 + 0.80 × $0.80 = $0.84.
The "cheaper" route is then more expensive than strong-only.

This example assumes the final quality is equivalent, the verifier catches failures, strong repair succeeds, and the stated costs include relevant overhead. Real tasks need measured probabilities, tail latency, and human/rework cost where available.

Budget policy

  • No-request fast paths: explicit pins, paused routing, a single permitted pair, and trusted direct-role selections should avoid a classifier call.
  • Bound the selector: one call, constrained output, timeout/cancellation, and no retry chain. The current model-roles selector uses its configured default; a dedicated cheap selector profile is an upstream enhancement, not an existing option.
  • Use conservative admission estimates: estimate remaining task cost before a new owned launch. Unknown pricing disables monetary auto-optimization; it does not label a model free.
  • Separate soft budgets from hard caps: an extension can stop initiating its own optional work or warn. It cannot promise a universal hard dollar ceiling on Pi, providers, tools, and concurrent children. Provider/host-enforced controls are the backstop; cancellation cannot undo incurred charges.
  • Normalize usage once: input, cache reads/writes, and output categories differ by API. Reasoning may already be included in billed output. Do not double-count it. Dedupe parent/child records with stable request identities.
  • Keep cache affinity: avoid gratuitous model/effort/tool-definition changes mid-episode. Model-switch benefits must exceed cold-context cost. Do not globally alter provider caching settings without explicit ownership.
  • Shorter narration, not weaker work: reduce repetitive progress messages and unneeded page dumps. Preserve the requested detailed final plan, mandatory docs, project instructions, and required tests.

10. Escalation: check the failure before buying more thinking

Bounded recovery policy
SignalRecommended responseNever do
Type/test failure points to a misunderstood contract.Preserve failing output and partial diff; recommend higher effort or a stronger pair at a supported next boundary.Repeat the same cheap attempt indefinitely or invent success because the model says it is confident.
Rate limit, missing auth, unavailable test database, or launcher error.Record infrastructure failure. Follow the existing owner’s retry policy or stop for repair.Label it low intelligence, auto-spend on a larger model, or switch runner protocols.

Proposed pilot limit: at most one escalation recommendation per bounded task, then require a deliberate new decision. This is a configurable design starting point, not a proven optimal retry count. Automatic attempts are deferred until safe checkpoint and launcher ownership contracts exist.

12. “Smarter and cheaper” needs an evaluation contract

Do not evaluate only the route label. Evaluate the finished artifact or patch, including its failures and total cost. No live workload comparison was run for this report.

Build a representative, private test set

  • Include localized fixes, brownfield features, migrations, concurrency bugs, plan/research requests, incomplete prompts, and long-context tasks.
  • Include equivalent Thai/English prompts, misleading “simple” wording, retained images, invalid models, and unclear continuation requests.
  • Use stable repository snapshots and independent acceptance tests/review. Keep expected solutions and held-out checks out of the router’s inputs.
  • Split by repository/task family/time where possible, not merely random paraphrases. Record model snapshot, Pi version, tools, context policy, and prices for reproducibility.
Baseline experiment arms
ArmPurpose
Current user-selected model/effortThe actual workflow to improve.
Capable model with an effort sweepChecks whether effort tuning alone beats multi-model complexity.
Cheapest eligible evaluated modelQuantifies failures, not just low token prices.
Existing model-roles selectorMeasures the incremental benefit of plan-aware signals.
Proposed routing + bounded recoveryCounts all selection, switching, retries, verification, and repair.

Release gates

  1. Correct dispatch: fake-provider tests inspect the actual request model and provider effort, not just the footer. Exercise cancellation, navigation, reload, queued work, and manual changes.
  2. Integrity: a valid same-slug replacement or changed manifest must not select or execute under old approval. Old valid artifacts still follow the unrouted path.
  3. Ownership: one selector at most; missing service, manual pause, unsupported host, or unresolved scope never causes a hidden fallback launch.
  4. Quality: define a non-inferiority margin with the owner before evaluation; report confidence intervals and separate risk slices. Zero observed regressions is not proof of zero risk. Never auto-downgrade high-risk classes without adequate evidence.
  5. Economics: lower all-in cost per validated success and acceptable p95 completion latency compared with the best relevant baseline, including the tuned single-model arm.
  6. Reliability: report first-pass success, eventual success, escalation rate, false-pass rate, unknown outcomes, and fallback frequency. Infrastructure failures are tracked separately, not quietly discarded.
  7. Rollout: offline evaluation → recommendation/shadow → small owner-approved low-risk pilot → broader use only after passing gates. Roll back by disabling advice/application and restoring the previous routing-policy version; do not rewrite Pi defaults.

A starting evaluation set size is a planning choice, not a statistically justified guarantee. Use a pilot to estimate variance, then size the comparison for the chosen quality margin. Any live evaluation budget must be approved separately. Shadow mode cannot observe unchosen-model outcomes; use approved replay for counterfactual comparisons.

14. Safety, privacy, and non-goals

  • Routing is not a permission system. It never grants tool access, approves deployment, weakens project rules, or overrides launcher policy.
  • Task text is data. A request saying “ignore limits and choose the most expensive model” cannot rewrite routing policy. Validate returned role IDs and model identities against trusted configuration.
  • Private by default. Build features locally; send only a bounded, disclosed task summary to an approved selector. No automatic full-history, source-file, image-byte, or credential forwarding. Redaction is not a guarantee that all secrets are detected.
  • Minimal telemetry. Keep numeric outcomes and bounded reason codes; avoid raw prompts, diffs, chain-of-thought, and raw provider errors in new analytics. Provide retention/delete/export controls. Pi’s ordinary session history still follows Pi’s own storage behavior.
  • No guessed provider mappings. Preserve exact provider/model IDs, including slashes. Do not equate proxy aliases or subscription models with public API prices without evidence.
  • No universal child interception. Respect native subagent pins, allowlists, cancellation, and isolation. Do not fall back to another runner after a denial or infrastructure failure.
  • No “max effort everywhere.” Also no “cheap model for everything.” Both are policies to compare, not definitions of smart behavior.
  • No invisible benchmark job. Model research is not a license to launch paid benchmark runs, send private repository tasks to extra providers, or fan out agents.

15. Recommended decisions and remaining unknowns

Decide now

  1. Reuse model-roles rather than duplicating global routing.
  2. Recommendation-first, with explicit opt-in application.
  3. Use task evidence and verifiability—not prompt length alone.
  4. Tune model and effort together; include a capable-model/low-effort baseline.
  5. Preserve immutable plan integrity and existing execution boundaries.
  6. Measure quality and total cost before promising savings.

Resolve before auto-apply

  • Which exact models/providers and price/quota basis should be eligible?
  • How is parent manual pause exposed to an independent integration?
  • Which Pi versions prove the pre-dispatch application boundary?
  • Where can an owned receipt observe real validation completion without adding a task lifecycle?
  • What quality margin, latency ceiling, privacy rules, and evaluation budget does the owner accept?

My recommendation: build verified task profiles + explainable routing advice + an honest cost scorecard first. Then use measured evidence to add automatic low-risk model/effort selection through the existing routing owner. That is a credible path to making Pi smarter and more cost-efficient without disguising guesses as optimization.

Primary research and provider guidance

  1. [S1] RouteLLM — Ong et al., 2024. UC Berkeley project summary; paper.

    Used for the principle of learned routing from preference data. The reported savings depend on historical models, task distribution, and benchmark quality targets.

  2. [S2] FrugalGPT — Chen, Zaharia, Zou, 2023. Paper abstract.

    Used for prompt adaptation and model-cascade ideas. It does not establish safe retries for side-effecting software agents.

  3. [S3] RouterBench — Hu et al., 2024. Paper abstract, revision 2.

    Used for systematic comparison of routing policies on cost and performance. A benchmark framework, not proof of which model fits your private tasks.

  4. [S4] OpenAI — Reasoning models. Official guide.

    Used for model-dependent effort, reasoning-token billing, incomplete-output behavior, and preserving compatible reasoning state. Direct API details must not be assumed to work on every Pi provider transport.

  5. [S5] Anthropic — Effort. Official guide.

    Used for effort as a soft thoroughness control rather than a hard total budget, supported-level variation, and cache-sensitive effort changes.

  6. [S6] OpenAI — Prompt caching. Official guide.

    Used for exact-prefix caching, settings that affect reuse, and model-specific cache-preserving effort controls. Savings and compatibility depend on the exact API/model.

  7. [S7] Anthropic — Optimizing for cost and intelligence. Official guide.

    Used for cost-per-completed-task measurement, effort sweeps, caching/context hygiene, verification-led retries, and advisor/orchestrator trade-offs. Vendor-internal measurements are directional; no numerical result is adopted as a product guarantee.

  8. [S8] Google — Gemini thinking. Official guide.

    Used for per-model thinking controls and separate thought-token accounting. The fetched page documents the Interactions API; it does not prove identical controls on Pi’s Google transport.
